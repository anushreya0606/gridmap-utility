1. Network & Data Terminology

Core electricity distribution network entities and data files.

Term Meaning Where You See It
Feeder An 11 kV line leaving a substation. It supplies many DTRs. Feeder code e.g. 100000000001
DTR / DT Distribution Transformer. Steps 11 kV down to the low voltage used by consumers. One feeder has many DTRs; one DTR supplies many consumers. DT code e.g. ABCD123456
Consumer A customer connection with a smart meter. Identified by the consumer (account) number. Consumer No e.g. 40000000001
Mapping Which feeder a DTR is connected to, and which DTR (and feeder) a consumer is connected to. Feeder → DTR → Consumer hierarchy
MI file (MI master) Meter Installation workbook from the utility. It holds the RECORDED mapping: sheets Total Consumer MI Data, Total DTR MI, Total Feeder MI. Genus Consumer MI Data.xlsx
Recorded mapping The feeder/DTR written in the MI file for a consumer or DTR. This is what the tool checks. Recorded Feeder, Recorded DT
Suggested mapping The feeder/DTR the outage timing points to when the recorded one looks wrong. A suggestion to verify in the field, not a final answer. Suggested Feeder, Suggested DT
Meter ID Serial number of the smart meter (consumer, DTR or feeder meter). Meter ID column
DTR meter / Feeder meter A meter installed on the DTR or on the feeder itself. It records when that DTR or feeder lost and regained power. Many DTRs have no meter (handled without penalty)
Outage report File listing power-failure events: consumer, DTR or feeder outage report. The type is detected automatically from the columns. Power Failure Report Consumer Meter.csv
Outage event One loss of power recorded by a meter: an off time and an on time. One row in an outage report
Off time (event_occurred) When the meter lost power. Feeder off, DTR off, Consumer off
On time (event_restored) When power came back. Feeder on, DTR on, Consumer on
Circle A utility administrative area (e.g. HARIDWAR_CIRCLE). Detected from the data, never hard-coded. Circle Name in the MI file

2. Feeder Breakdown Check Terminology

Verification of elements inside the feeder breakdown time window.

Term Meaning Where You See It
Feeder breakdown One outage of a feeder, from its feeder meter: feeder off time to feeder on time. Breakdown e.g. 100000000001 @ 16-10 17:32
Breakdown window Feeder off time minus tolerance, to feeder on time plus tolerance. Anything below the feeder should go off inside this window. e.g. 17:30 to 17:41 for a 17:32–17:39 breakdown
Tolerance Extra minutes allowed because meter clocks are not perfectly in sync. Default ±2 minutes; can be adjusted in New Run settings. Timing tolerance (minutes)
Breakdown (min) How long the feeder breakdown lasted, in minutes. Breakdown (min) = 7
Feeder → DTR check For each feeder breakdown: did each DTR recorded on that feeder go off inside the breakdown window? Feeder_DTR_Breakdowns sheet
Feeder → Consumer check For each feeder breakdown: did each consumer recorded on that feeder go off inside the breakdown window? Feeder_Consumer_Breakdowns sheet
DTR → Consumer check For each DTR that went off in a breakdown: did its recorded consumers go off inside the DTR's own off-on time? DTR_Consumer_Breakdowns sheet
MATCH It went off inside the window, as the recorded mapping predicts. On per-element sheets: it went off in EVERY breakdown checked. Green cell / pill in summary
MISMATCH It had data that day but did NOT go off inside the window — a sign of wrong mapping. On per-element sheets: it went off in NO breakdown. Red cell / pill in summary
PARTIAL Per element: went off in some breakdowns but not all. Could be a data/meter issue or wrong mapping — worth a look. Yellow cell / pill
No data (not counted) Cannot be judged, so it is NOT counted as match or mismatch: NO DTR METER, NO METER DATA or FAULTY METER. Summary column
NO DTR METER The DTR has no DTR meter installed, so we cannot know when it tripped. Feeder_DTR_Breakdowns, Result column
NO METER DATA The consumer's meter sent no outage event at all that day, so it cannot be judged (it may have been offline). Feeder_Consumer_Breakdowns, Result column
FAULTY METER The meter reported too many outages in one day (default >40); it is excluded as flapping/unreliable. Faulty_Meters_Excluded sheet
Match % MATCH / (MATCH + MISMATCH). No-data rows are excluded to preserve statistical integrity. Summary sheet
Breakdown checks (rows) Number of (breakdown × element) checks. A DTR on a feeder with 3 breakdowns is checked 3 times. Summary sheet
Unique elements checked Number of distinct DTRs or consumers that could be judged, each counted once. Summary sheet
Always matched Element went off in every breakdown it was checked in: mapping confirmed. Summary sheet
Partly matched Element went off in some breakdowns, not all. Summary sheet
Never matched Element did not go off in any breakdown: strongest sign of wrong mapping. Summary sheet
Exact timing Off AND on time both within the tolerance of the feeder's (or DTR's). The strongest kind of match. Exact timing (off & on within tol)
Off diff (min) Element off time minus feeder (or DTR) off time, in minutes. Off diff (min) = 0.5
Breakdown status Whether a feeder breakdown record can be trusted: Confirmed, SUSPECT BREAKDOWN or Not verifiable. Breakdown_Status sheet
Confirmed (breakdown) At least 10% (default) of the feeder's own consumers went off. A verified breakdown; its results are reliable. Breakdown_Status sheet
SUSPECT BREAKDOWN Fewer than 10% (default) of the feeder's own consumers went off. The breakdown record or feeder meter is doubtful (e.g. meter on another feeder), so its mismatches do not prove wrong mapping. Breakdown_Status sheet
Not verifiable (breakdown) No consumers with data are recorded on that feeder, so the breakdown cannot be confirmed or rejected. Breakdown status column
Own consumers that went off (share) Of the feeder's recorded consumers that sent data, the share that confirmed power failure during the breakdown. Breakdown_Status sheet
Confirmed breakdowns only The exact same counts, leaving out suspect breakdowns. Summary sheet, second table
Counts based on Per-feeder counts use only confirmed breakdowns; if ALL of a feeder's breakdowns are suspect, they are marked 'treat with care'. Feeder_Summary sheet
DTR went off (breakdowns) How many of the feeder's breakdowns the DTR went off in, e.g. 2/3. Feeder_DTR_Counts sheet
Feeder_Summary One row per feeder: number of DTRs and consumers and how many MATCH, PARTIAL, MISMATCH or have no data. Sheet name in Excel
Feeder_DTR_Counts Same as Feeder_Summary, opened up per DTR. Use the 1/2 buttons at the top-left of Excel to collapse/expand. Sheet name in Excel

3. Wrong-Mapping Identification Terminology

Outage pattern matching across candidate sources.

Term Meaning Where You See It
Outage pattern matching A consumer's outages are compared with the outages of every DTR and feeder. Two outages match when off AND on time are both within tolerance. Mapping_Report.xlsx
Outages followed (x/y) The consumer went off in x of the y outages of that candidate DTR/feeder. Recorded DT outages followed = 0/4
Score How well two outage histories agree, from 0 (never together) to 1 (always together). Computed as Jaccard overlap: shared outages / all distinct outages of both. DT score (recorded)
WRONG The consumer follows another DTR/feeder clearly better than its recorded one (≥60% of the other's outages, ≤40% of the recorded one's, score gap ≥ 0.25, ≥ 2 shared outages). DTR check / Feeder check column
LIKELY WRONG Same as WRONG, but the recorded DTR/feeder had no usable outages, so the evidence is one-sided. DTR check / Feeder check column
OK (mapping) The consumer follows its recorded DTR/feeder; no better candidate found. Results
NOT EVALUABLE Too few outages (fewer than 2) to judge. Results
GROUP ISSUE (check source meter) Most consumers of this DTR/feeder disagree with its meter, so the METER is probably wrong, not the consumers. DTR check / Feeder check column
Confidence (High / Medium / Low) How strong the evidence is that the RECORDED mapping is wrong. High: ≥3 shared outages and large score gap. Medium: clear but smaller. Low: one-sided evidence. Confidence column
AMBIGUOUS (n) The consumer follows n DTRs equally well (they share the same feeder outages). The feeder is clear but the exact DTR needs a field check. Suggested DT
Candidates The DTRs/feeders tied for best match (first 5 shown). Candidates column
Peer-group DTR events For DTRs without a meter: moments when ≥50% (and ≥3) of the DTR's own consumers went off together. A consumer never counts in its own group's evidence. Progress log
Mismatch_Patterns Many consumers moving the same way (recorded feeder → suggested feeder). Large groups usually mean a records error, not many separate wiring errors. Sheet name
Suspect_Source_Meters DTR or feeder meters that are probably installed on a different DTR/feeder than recorded. Sheet name
DTR_on_Wrong_Feeder DTRs whose own meter follows another feeder's outages. Sheet name
Faulty_Meters_Excluded Consumer meters with too many outages in one day (default > 40). Sheet name
Not_in_MI Consumers in the outage report that are not found in the MI master file. Sheet name
Feeder_Event_Check For each feeder outage: how many of its own consumers followed it, and which other feeder's consumers followed it most. Sheet name

4. DTR → Feeder Check Terminology

Independent verification of whether each DTR is on its recorded feeder.

Term Meaning Where You See It
Meter check Did the DTR's own meter go off with its recorded feeder's outages? DTR_Feeder_Check sheet
Consumer check Do the DTR's consumers follow the recorded feeder? Needs at least 3 consumers with a feeder-level test. DTR_Feeder_Check sheet
CORRECT The checks confirm the DTR is on its recorded feeder. verdict column
WRONG (both / meter / consumer) The DTR seems to be on another feeder; the brackets indicate which evidence confirmed it. verdict column
CONFLICT One check says correct, the other says wrong. Requires an on-ground field check. verdict column
FEEDER METER ISSUE The DTR looks wrong only because a feeder meter is on another feeder; the DTR itself is probably fine. verdict column
UNCLEAR There is some data but it is not statistically decisive. verdict column
NOT CHECKABLE No usable outage data for this DTR (its feeder had no recorded breakdown, or the DTR has no meter and too few consumers with data). verdict column
% correct of DTRs judged CORRECT / (CORRECT + WRONG + CONFLICT). Summary sheet
records_disagree The DTR MI sheet and the Consumer MI sheet give different feeders for the same DTR. DTR_Feeder_Check sheet

6. Data Quality Checks & System Terminology

Verification of uploaded files and system mechanics.

Term Meaning Where You See It
Data checks Checks run on every upload: readable dates, period covered, coverage in the MI file, duplicates removed, shared days between files. Data_Checks sheet / results page
OK / WARNING / ERROR OK = fine. WARNING = results still produced but may be weaker. ERROR = the data cannot be checked; the run stops with an explanation. Status column
Coverage Share of consumers/meters in the outage files that are found in the MI file. Low coverage usually means files from different circles. Data checks
Period covered First and last date in a file, and the number of days. Data checks
Duplicate rows removed Same meter with the same off time listed more than once; counted once. Data checks
Stored events Every uploaded outage event is saved so past days can be analysed again together with new ones. The same event is never stored twice. Stored events page
Events analysed (scope) Which events a run used: only files uploaded now, all stored events, the last N days, or a date range. Results page
Past runs Every run with its results and Excel files, preserved across server restarts. Past runs page
Private workspace On a public deployment, each browser has its own isolated runs and stored events (kept with an encrypted cookie). Others cannot see them. Deleted after 7 days without use. New run page
Rules used The thresholds applied in a run (tolerance, suspect %, faulty-meter limit, wrong-mapping limits). Printed with every result so anyone can audit them. Results page / Summary sheet

7. Mathematical Rules & Verification Engine

Detailed algorithmic logic behind the analysis engine.

Breakdown Window Evaluation

An element \(e\) (DTR or Consumer) is judged against a Feeder Breakdown starting at \(S_f\) and restoring at \(E_f\) with tolerance \(\Delta = 2\text{ min}\):

  • MATCH: \(\exists\) outage on \(e\) starting at \(S_e\) such that \(S_f - \Delta \le S_e \le E_f + \Delta\).
  • MISMATCH: Element \(e\) reported at least one event that day but did not trip within \([S_f - \Delta, E_f + \Delta]\).
  • NO DATA: Element \(e\) has no meter installed or sent zero events that calendar day. Never counted as mismatch.

Jaccard Outage Pattern Matching

For consumers with multiple trips, similarity with candidate source \(s\) is calculated via Jaccard overlap:

J(c, s) = |Outages(c) ∩ Outages(s)| / |Outages(c) ∪ Outages(s)|

Flagging requires \(\text{Recall}(s) \ge 60\%\), \(\text{Recall}(\text{rec}) \le 40\%\), and a score gap exceeding 0.25.
